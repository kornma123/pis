# COREONE Issue 分级与上线阻断标签规则

<!-- issue-rating-contract-id: coreone-issue-rating/v1 -->

## 1. 目的与适用范围

本文件是 COREONE Issue 评级与上线影响标签的**唯一详细规则源**；其他流程文档只指向本页，不复制双轴定义。进入实现的 Issue 必须同时标记两个相互独立的维度：

1. 一个优先级标签：`P0`、`P1`、`P2` 或 `P3`；
2. 一个上线影响标签：`阻断上线` 或 `非阻断上线`。

默认“上线”指首次正式生产或外部试用。若某一阶段另有经过 PM 确认的 release target，以该目标为准，并在对应 Issue 中写明。

优先级表示问题本身的严重程度；上线标签表示该问题是否必须在目标上线前闭合。两者不得混为一个维度。

只有仍在澄清问题、尚无可实施范围与 AC 的 `question-only` 讨论 Issue 可以暂时只带 `question`、不带双轴。它不得被认领或开工；由 Codex 完成去重、事实、范围、AC 复核和正式评级后，才转成可实施 Issue。

## 2. 优先级定义

| 标签 | 定义 | 典型情形 |
|---|---|---|
| `P0` | 已证实的最高严重度问题，必须立即进入主线处置 | 系统持续无法启动；关键账本、金额、库存或权限事实可被确定性破坏；重大安全边界失守；没有安全绕行方案 |
| `P1` | 核心业务、安全、数据完整性或关键流程缺陷 | 关账、对账、采购、库存、成本、权限、审计等核心事实可能错误；关键验收门缺失；需要优先修复但尚未达到 P0 |
| `P2` | 重要但影响有界的能力、证据或体验缺口 | 有安全降级或明确人工兜底；定向提示、证据机器化、后续能力、非关键流程准确性问题 |
| `P3` | 延期功能、清理或非紧急治理事项 | 已退役合同清理、未来 wave、当前发布范围外的 PRD 债或低风险维护项 |

约束：

- 不得为了“看起来重视”而把未验证风险升级为 `P0`。
- `unknown`、环境阻塞或缺少运行证据不得自动降级为低优先级；应先保留真实的 `BLOCKED`/`NO_GO` 状态并补证据。
- 优先级依据可复现影响、触发条件和业务后果，不依据实现工作量或排队时长。
- `P0 + 非阻断上线` 与 `P3 + 阻断上线` 默认非法；不得用互相冲突的双轴掩盖处置决定。

## 3. 上线影响定义

### `阻断上线`

存在以下任一条件时使用：

- 未闭合时可能发布错误金额、库存、权限、审计或关账事实；
- 属于首次外部试用明确要求的安全硬门；
- 会导致目标环境无法启动、升级或稳定运行；
- 是目标发布所需的真实证据、财务认账、独立验收或回归门；
- 没有经过批准、可审计且不会扩大风险的临时降级方案。

### `非阻断上线`

仅在满足以下条件时使用：

- 不影响当前目标发布的核心业务正确性、安全性和数据完整性；
- 有明确、安全且不会把 unknown 伪装成 success/zero 的降级行为；
- 属于后续迭代、延期 PRD、低风险治理、已合并后的残余体验或清理事项。

`非阻断上线` 不等于“不做”，也不等于 Issue 已完成。

复核 finding 是否阻断当前发布，必须独立评估真实可达性、当前 AC / 明示 threat contract、业务/安全/数据影响和安全降级。当前 AC / 明示 threat contract、现实可达或高影响问题保持阻断；人工改库、移除 trigger、异常历史脏数据或极低频怪异输入，只有在影响被证据证明可控且不违反前述合同后，才可去重转成 `非阻断上线` follow-up。

## 4. 双轴组合示例

- `P0 + 阻断上线`：确定性系统不可启动或关键账本可被破坏。
- `P1 + 阻断上线`：核心业务真值、安全硬门或关键回归门未闭合。
- `P1 + 非阻断上线`：需要尽快修复的活跃治理失真，但不影响当前运行时能力。
- `P2 + 阻断上线`：问题本身影响有界，但它是当前发布必须取得的外部证据或验收条件。
- `P2/P3 + 非阻断上线`：后续能力、体验优化、延期 PRD 或清理事项。

## 5. 标注与复核流程

1. 新建 Issue 时，创建者给出建议优先级和上线影响，并写明触发、影响及依据；`question-only` 只声明问题与待澄清边界，不伪造实施评级。
2. Issue 进入实现前，Codex 负责去重、事实、范围、AC 复核，作出正式双轴评级，并以唯一 GitHub 写入 owner 身份串行写入和回读标签。PM 保留产品范围、业务风险接受和 release target 的决策权，但不替代该操作责任。
3. 每张可实施的开放 Issue 必须恰好拥有一个优先级标签和一个上线影响标签；不得缺失、重复或使用非法组合。
4. 出现新运行证据、范围变化、核心部分已合并、目标 release 改变或安全降级方案获批时，Codex 必须重新评估并写入审计评论：

   ```text
   [ISSUE-RATING] owner=Codex previous=<P?/上线影响|UNRECORDED/UNRECORDED> current=<P?/上线影响> reason=<具体依据>
   ```

5. 活动任务遇到合法评级变化或旧版 state 缺少评级字段时，不得静默接受或覆盖 state。先核对 Issue body、owner、branch、base 未变化，再运行 `node scripts/claude-task.cjs rebaseline-rating --evidence=<上述普通评论 URL>`；范围/body、owner、branch 或 base 变化仍须走正式 handoff / 重新认领，不得借评级迁移绕过。
6. Issue 关闭前仍以 GitHub 实时状态为准；本文不保存动态 Issue 数量、当前分支、测试计数或完成度快照。

## 6. GitHub 写入纪律

- 标签修改是正式 GitHub 写入，只由 Codex 作为当前唯一 GitHub 写入 owner 低频串行执行；写前运行 offline governance，写后回读两个维度。
- 不用 workflow 或外部 AI 自动发布 review、comment、status，也不把 GitHub 当模型间实时聊天渠道。
- 标签变更不等于实现、独立复核、合并、发布或生产授权。
- 若标签与 Issue 正文的稳定风险结论冲突，先修正文或形成 PM 决策，再修改标签，不得静默掩盖冲突。
