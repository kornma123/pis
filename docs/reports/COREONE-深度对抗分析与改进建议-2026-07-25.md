## 1. 硬问题清单（按杀伤力排序）

### F1 【机制】master 没有任何机器合并门——"required checks"是散文，不是闸

- **质疑**：契约 §7、pr-governance §5、golden-registry.md:9 都说"required checks 满足才可合并"，registry 甚至写明"master 分支保护 required status check = `vitest`（enforce_admins=false）"。但 GitHub 现场：**无分支保护、无 ruleset**（N1/N2）。`vitest/gate/e2e-required/secret-scan` 四个绿勾对合并按钮没有任何强制力。
- **证据**：LIVE_VERIFIED（API 404 + 空 rulesets）；registry 原文golden-registry.md:9 [AUTHORITY_DEFINED，与现实相反]。
- **影响**：合并纪律 100% 靠自律。#64 零 review、零评论直接 merged（上轮已证）不是偶然违规，而是**机制允许下的必然**——只要任何会话（人或 AI）一时手滑或过期理解，就能绕过整个复核体系推到 master。对一个把"异构复核"当命脉的项目，这是地基级缺口。
- **建议**：PM 在 GitHub Settings 建一条 ruleset（要求 4 个 checks 通过 + 禁 force-push + 禁删除 master；solo 阶段可不加 required review，但 checks 必须硬）。这是 5 分钟的人工设置，不需要写码；同时按 GOV 纪律登记 registry:9 的失实转录。

### F2 【脱敏】公共仓库里实名医院 + 精确财务值仍在 `golden-registry.md`

- **质疑**：仓库是 **public**（N3）。PRD v1.6 头部 PUBLIC 脱敏边界明确"不点名账户、不重复精确医院财务"，其 K-1/K-2/K-3 行也确实只写"具体财务值不在本 PUBLIC PRD 重复"——但它指向的 `golden-registry.md:15–17,26–28` 公开写着**实名医院名称与多条精确结算/分账金额**（本文刻意不转录，见 registry 原文）。脱敏边界在 PRD 里执行了，在它引用的 registry 里没有。
- **证据**：LIVE_VERIFIED（public 属性 + 文件在 master）；PRD 脱敏边界原文 [AUTHORITY_DEFINED]。
- **影响**：客户（医院）身份与真实结算金额的公开暴露，属于 P- 系列隐私/合规决定的管辖范围；若是漏网，需要处置（脱敏改写或仓库转私有）；若是拍板过的"既有公开源保留"，PRD 那句"已在其他仓库文件出现不构成再次披露授权"应当显式覆盖 registry，否则边界自相矛盾。
- **建议**：PM 明确回答（见 grill 问 2）。这不是代码问题，是合规判断，任何 AI 不应自行改写 registry。

### F3 【文档漂移】顶层 PRD v1.6 与 GitHub 现实脱节——最重要的工程线已闭环，PRD 还说"待推进"

- **质疑**：#1/#2/#3 均已 CLOSED、PR #59（批次库存事实）/#54（跨月分摊）/#62（Phase 1A 台账）已合入 master（N6，上轮 LIVE_VERIFIED）。但当前 master 的 PRD v1.6：§4.1 仍写 LOC-001 是"当前唯一工程入口…远端 integration 分支或本地候选均不等于 master 完成"；§11 Now 仍列"LOC-001 按已拍 A 模型推进…作为真实数据进入前的硬前置"、"LOC-002 承接 #163 阶段 2"；`本地Issue指导` 仍写三票 `REMOTE_INTEGRATION_NO_GO`。
- **影响**：每个新会话（包括本工具第一轮）都会从权威链读到**过期一周以上的工程状态**，直接污染派工判断。PR #73 只修了"执行顺序"，没修 §4/§11 的实质状态。项目有 drift-gate 治理（GOV-002 管 PM 待拍板索引），但**没有覆盖 PRD 自身对工程票的转录**。
- **建议**：①走 PRD Loop 修订轮出 v1.7，把 #1/#2/#3 完成态与剩余边界（LOC-036 盘点、LOC-020 等）如实转录；②把"PRD §4/§11 对 live Issue 状态的转录"纳入 drift-gate 范围（GOV-002 的验收正好缺这块）；③在 v1.7 之前，任何引用 PRD 工程状态的会话必须以 GitHub 现场为准（本文即为一例）。

### F4 【产能】非作者 R2 是系统性瓶颈：一边干等、一边绕过

- **质疑**：当前两张 Draft PR（#74 ABC 退役、#75 月结原子性）checks 全绿但 reviews=0，干等非作者 fixed-SHA R2；而 #64 在同一天以零可见复核合并。同一个体系里，"等 R2"和"不要 R2"并存，说明 R2 供给不足且**没有队列、没有 SLA、没有配对**。
- **影响**：R2 是全项目最稀缺的资源，却没有被当资源管理。主线每个 P0/P1 票都要过这道门；不解决，10-31 目标（F5）必然落空或被迫降级纪律。
- **建议**：把 R2 当一等公民排产——每张实现票派工时**同时指定 reviewer 配对**；用 Issue 标签或看板做 R2 队列可视化；给 R2 设响应时限；#64 式"零可见复核合并"要么补登记线下 L0 证据链，要么承认例外并留痕。

### F5 【时间线】2026-10-31 第一个真实解锁院月：应按"乐观上界"管理，不是计划

- **质疑**：串行依赖链 = B（08-31 固定成本池真实金额+管理员认账，外部证据）→ C2–C4（真实 finality 信号+三期 verified+首周期独立验收）→ D1（历史月四态）→ D2（09-30 目录+金额 manifest）→ E1（生产三态前端）。每一环都卡在**自己控制之外的证据**或**稀缺复核产能**上；且规则是单 owner 串行。O-5 的顺延机制是诚实的，但内部预期管理应把 10-31 标为乐观上界。
- **证据**：AUTHORITY_DEFINED（PRD §11、本地 Issue 指导 §7 全部标 BLOCKED_DEPENDENCY/EXTERNAL_EVIDENCE）+ INFERENCE（产能判断）。
- **建议**：倒排一个"最小可信解锁"的降级方案：如果 10 月只有一家全流程医院、一个周期凑齐证据，能不能先解锁这一家一月？把"三个可回溯周期"的硬门与"最小经营可读版"分开讨论（这需要 PM 拍板，属方向级）。

### F6 【产品逻辑】最锋利的缺口：算不出的账户，可能正是决策密度最高的账户

- **质疑**：贡献毛利只覆盖"本院做了技术工序"的 case；纯代送/会诊/外送收入全部落入 UNMEASURED（在册、可排后、不可漏）。系统的设计承诺是"不排名、不打分、人去做去留/谈价判断"。Grill：**纯代送账户恰恰是最需要谈价/重议合作形态的账户**——它们结构不同、议价空间最大，而系统对它们只能说"看不清"。
- **证据**：AUTHORITY_DEFINED（CONTEXT.md UNMEASURED 定义："须配独立复核节奏、并为其建符合成本结构的独立盈利口径（另立项）"）。
- **影响**：第一个解锁月到来时，PM 手里是一叠"可测账户的精确答案"+一叠"最需决策账户的空白"。CONTEXT 已把"UNMEASURED 独立口径"列为复活双触发之一，但它目前连 Issue 都没有。
- **建议**：把"UNMEASURED 独立盈利口径"的**立项评估**排进 Next（不是实施，是先回答"代送口径需要哪些数据、能否拿到"）；评估入口条件=PM 提供纯代送账户的收入占比量级（grade C 内部探索即可）。

### F7 【环境】这台 Mac 的工作区是"脏交接面"，且在 Syncthing 同步之下

- **质疑**：契约 §8/§9 说跨设备交接**只承认进入 GitHub/Git 的状态**。但本地：落后远端 16 个提交、30 条 dirty/untracked（含**已暂存**的 `claude-task.cjs` 机制改动与 `.bak`/`.orig` 残件）、`.stversions` 508MB 证明整个工作区在 Syncthing 同步下（N7）。Syncthing 会把未提交碎屑同步到其他设备，制造"文件存在但 GitHub 不承认"的灰状态；dev SQLite DB 在同步目录下还有冲突/损坏风险。
- **影响**：跨设备纪律有一个未登记的旁路；脏暂存区随时可能被某个会话误带进提交。
- **建议**：①PM 确认 Syncthing 同步是否有意——若是，建议把仓库目录从同步中排除，跨设备只走 Git；②认领或丢弃 staged 的 `claude-task.cjs` 改动（它是机制脚本，按契约先写自测）；③`.bak`/`.orig`/`.codegraph` 等残件清理或入 `.gitignore`。

### F8 【架构】SQLite 单写者 × 真实业务并发：上线前必须回答，现在可以记账

- **质疑**：`node:sqlite` 单文件单写。开发阶段无并发问题；但路线图上"真实数据进入"后，仓管/技术员每日出入库 + 财务月结导入 + 盘点会在月末撞同一把写锁；月结原子性（#5）和 migration predecessor ledger（PLATFORM-R1，P0）正是在补这块的地基。
- **证据**：AUTHORITY_DEFINED（guardrails 数据库规范、PLATFORM-R1 票）+ INFERENCE（并发推演）。
- **建议**：不提前优化，但在 LOC-022 安全硬门同档登记一条"真实进入前的并发/锁行为验证"验收项，明确第一个真实使用日的场景（谁先谁后、月结窗口多长）。

### F9 【文档考古层】根目录 5 月遗留文档无拦截头，是新会话的误导源

- **质疑**：《待办清单.md》《待处理清单.md》（2026-05）写着"确认入库仅 toast 不调 API""退库/报废/调拨无页面"——现状这些页面都已存在（前端 pages 目录现场确认 returns/scraps/transfers 均在）。README 已给 GITHUB-WORKFLOW-GUIDE 等加了 SUPERSEDED 头，但这两份（以及 E2E-* 系列）没有。**本工具第一轮就被它们误导**，把它们当"当前问题"汇报过——这是已发生的实际损害，不是假设。
- **建议**：R0 级文档处置：加 SUPERSEDED 阻断头（注明替代权威）或移入 `docs/archive/`；同时把"根目录考古文档清单"并入 GOV 治理。

### F10 【交付面】页面复杂度已接近商用 SaaS，而 E2E 回归网还没重建

- **质疑**：前端 pages 目录 30+ 个路由（含 `_laneC`、hospital-cm、import-console/wizard/shared 等），但 e2e impact planner 对 legacy 域 fail-closed、夜间全量尚无具名 owner（M-1 决定）。内部 7 角色工具，每多一个页面就多一份回归债。
- **建议**：上线前做一次"页面→角色→日频"裁剪：非日频页面能藏则藏（导航级，不删代码），把 E2E critical spec 集中在日频路径。这是产品决策，列入 Next 讨论。
