## 1. IMPL-1【同一原则，只修了一半】hospital-cm 的 LIS 计数字段仍用 `Number(x) || 0` 折 0

- **已拍原则**：LOC-002 的 Windows 高风险探针确立——跨月权重「不得用 `Number(lab_revenue) || 0` 把 malformed/non-finite/unsafe 数据折为 0 或污染权重；必须以行为测试证明 fail-closed」（本地 Issue 指导 §LOC-002；修复在 integration `392e05ad`，随后 PR #54 合入）。
- **现状（CODE_CONFIRMED at master）**：`utils/hospital-cm-service.ts:262–264` ——
  ```ts
  specialStainCount: Number(r.special_stain_count) || 0,
  blockCount: Number(r.block_count) || 0,
  ihcCount: Number(r.ihc_count) || 0,
  ```
  这些 LIS 工作量计数（特染片数/蜡块数/IHC 片数）进入 `P0CaseInput`，驱动桶 A/桶 B 成本分摊基数。一条 malformed 的 LIS 行会被**静默按 0 片**处理：成本分摊偏移、无错误、无信号。
- **质疑**：同一个「malformed 不得折 0」的已拍原则，收入权重修了，计数字段没修。这是口径问题而非明显 bug——片数折 0 与收入折 0 的伤害方向不同（收入折 0 是少算钱，片数折 0 是分母失真），需要一句明确的口径裁决：LIS 计数字段 malformed 时应 fail-closed（整例扣留/质量标记）还是允许按 0 并留痕。
- **是否已被裁决过**：UNVERIFIED——LOC-002 的探针与修复范围按文档只覆盖权重路径；未见针对这三个计数字段的明确决定。
- **建议**：在 #15（LOC-015 D2 金额/证据收口）或单独小票中补一句口径裁决 + 行为测试；不自行改码。
- **Root 裁决（2026-07-25）**：✅ **已采纳**——Issue #15 已纳入 `hospital-cm-service.ts`、`partner-pnl-service.ts`、`reconcile-compute.ts` 的运行时数值真值合同（unknown 不得折 0），并明确不得恢复 ABC 人工/折旧/场地成本。

## 3. IMPL-3【正面】错误响应 5xx 脱敏、4xx 透传，方向正确

- **CODE_CONFIRMED**：`utils/response.ts:44` —— 5xx 在非 development 环境统一替换为「服务器内部错误，请稍后重试」，details 只在 dev 输出；路由层 `catch (err) { error(res, err.message) }` 默认 500，因此内部错误细节不会出网。
- **观察（非问题）**：业务校验失败若也走默认 `error(res, message)` 会成 5xx 而非 4xx，语义粗糙但不泄密；各路由已有意传 4xx 的地方（如出库算术超限 400）是对的。

## 4. IMPL-4【正面】出库写路径是事务纪律的样板

- **CODE_CONFIRMED**（routes/outbound-v1.1.ts:236–300）：`BEGIN IMMEDIATE` → 同事务幂等 claim（`claimIdempotency`）→ `planInventoryDeductions` 统一规划扣减（FEFO）→ 算术复查失败即 `ROLLBACK` + 400 → 逐行写 outbound_items/stock_logs（带 before/after）→ `applyInventoryPlan` 落批次。入库同样多入口 `BEGIN IMMEDIATE`。
- **轻量观察（非阻断）**：`batch_usage_tracking` 的 ID 用 `TRK-${Date.now()}-${Math.floor(Math.random()*1000)}`——随机空间只有 1000，同日同物料并发时有撞号理论风险；这是 ID 生成（非展示数字，与 PF1 的随机环比性质完全不同），建议顺手改 uuid，R0 级。
